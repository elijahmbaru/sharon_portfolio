The goal

Help User Ops answer merchants with accurate payout information, and send fewer tickets to engineers.

Settlements in Nigeria are operations heavy, and Paystack relies on many partners for collections, settlements and payouts. Resolving a payout issue was slow, and User Ops needed engineers to decode errors, estimate how long a fix would take, and decide whether to contact the bank or the merchant.

Objective 01

Give the payout operations team accurate payout information, in tools they can reach, so they can respond to merchants.

Objective 02

Reduce tickets escalated to engineers for decoding error codes, updating payout statuses and retrying payouts.

The problem

Only a few engineers could fix payout issues, and teams found out late

~70%of all platform requests come from daily settlement operations
~15%of daily payouts get stuck in processing, are reversed, or fail without an automatic retry
1way for User Ops to learn about a stuck payout: a merchant complains. Retrying it depended entirely on engineers.

01 · Discovery

How payout issues get resolved today

Research

We interviewed the User Ops team about how they resolve payout issues

Issues are spotted by merchants, User Ops or engineers. Wherever they start, they pass to engineers to troubleshoot, then back through User Ops to the merchant, and sometimes to the processor or bank. Along the way the work hops between Slack, Jira, Metabase, Zendesk and Watchtower.

Synthesis

User Ops owned the merchant conversation, but not the information

Primary needs

  • A clear understanding of the problem, so they give the merchant accurate information
  • Visibility of a payout's status, for internal escalation and for replying to the merchant

Challenges

  • No visibility of the information needed to decode errors
  • Limited access to tools like Metabase that explain why a payout has an issue
  • No way to retry failed payouts

Give User Ops the visibility and the controls to resolve payouts themselves.

02 · Prioritisation

Choosing which requests to tackle first

Prioritisation board

We grouped every request type, then mapped constraints and solution ideas

Error handling came first: payouts stuck in processing, changing processors, NIBSS batch ID requests, retrying failed payouts and Wema error codes. Other groups included acquirer settlement debt, reversed payouts, oversettlement and status updates.

03 · Solutions

Visibility and control, all on Watchtower

Recommendation 1a · Visibility

Show decoded errors, a timeline of trials, and the account details that matter

Error codes and their meaning now sit in the payout's audit logs. Successful payouts show their session ID. Failed ones show the processor, the error code and the reason.

Recommendation 1b · User control

Let User Ops update statuses, retry payouts and apply deductions

Three actions cover the requests that used to go to engineers. Each has clear rules, and every action is written to the logs.

Update payout status

When

  • Watchtower's status doesn't match Metabase
  • A payout shows “success” but was reversed
  • A payout is stuck in processing but failed at the processor

Rule

A payout in processing can only be updated once its final state is confirmed with the processor.

Retry payout

When

  • A payout has failed
  • A payout has been reversed

Rule

Only failed payouts can be retried. User Ops can keep the current processor or switch, for example from NIBSS to Wema.

Apply a deduction

When

  • Paystack refunded a customer for a chargeback or refund
  • A merchant received an over-settlement

Rule

The merchant is notified automatically. If their balance is too low, the rest is deducted on the next payout cycle.

Where the actions live

We explored two placements: a modal opened from an Action button, and a dedicated Action tab beside the logs, shown at the top of this page.

The flows

Small forms, clear rules, and a record of every change

Updating a status asks only for the new status and a reason. A retry is offered once every trial has failed, after five attempts. If a payout was split, all of its trials must fail first, otherwise it’s escalated. A deduction can’t be applied without a link to the merchant’s consent ticket. It can be cancelled from the audit logs with a reason, unless it has already been processed.

Recommendation 2

Get ahead of merchant complaints

Alert User Ops

Notify the team when a payout has an issue, so they can reach out first.

Tell merchants early

Share delays and resolutions on the merchant dashboard or by email.

Explain the why

Keep a living guide to error codes that the whole team can use.

04 · Outcome

Shipped: NGN payouts can now be retried on Watchtower

What shipped

User Ops can now retry Nigerian payouts stuck in processing directly on Watchtower, and see more detail about each payout trial handled by the settlement engine.

Payouts stuck in processing were the biggest payout issue in Nigeria, and the inconclusive state meant a person had to step in. Putting the action on Watchtower lets User Ops handle these without relying on engineering or product.

Expected results

  • Fewer payout-related requests to the platform team
  • Faster answers to merchant queries
  • Clearer information on a payout's state and how many times it was retried, for handling disputes
